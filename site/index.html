Open source, Apache-2.0

Binary messages off the wire, decoded, for anyone who needs them

first-bite listens on a tap or a mirror port, local or tunnelled (ERSPAN/GRE), decodes fixed-layout binary messages against a dictionary, and publishes each one as a JSON record that any number of consumers can subscribe to. It never transmits on the capture interface, and one core handles 340,000 packets per second.

It listens, and takes nothing from the link

first-bite opens the capture interface for reading and never sends on it. On a passive tap there is no path from the monitor ports back to the link, so nothing first-bite does can delay, block or alter the traffic between the native systems, and if it stops, the link is unaffected.

Where a tap cannot be fitted, a switch mirror port gives the same copy: forwarding is not affected, but the switch does the copying and drops mirrored frames first when it is busy. A remote mirror sends the copy in an ERSPAN, GRE or VXLAN tunnel to first-bite on another host, which unwraps it; that adds the mirrored traffic to the network carrying the tunnel. It was built to open up the traffic of a tactical local network that until then was visible only to the systems exchanging it.

The message set is data, not code

A dictionary is a directory of JSON files that gives the bit range, type and value labels of every field. The same binary decodes a weather station's UDP reports, the frames on a vehicle CAN bus or a message set of your own, and bite check validates a dictionary and runs the test vectors it carries.

One core is far more than a link needs

The whole pipeline (read a frame, parse Ethernet, IP and UDP, decode, build the JSON record, publish) takes 2.9 µs per packet. A link carrying 1,000 messages per second therefore uses about 0.3% of one core, and a record is on the bus about three microseconds after its frame is read.

The project's first decoder managed 194 messages per second. The current one decodes 1,700,000 on the same recorded messages, and also decodes the fields the first returned as null.

One decode, any number of consumers

Without a tap, each consumer of a binary interface writes its own parser and holds its own connection to the native system. With first-bite the decode happens once: consumers subscribe to a ZeroMQ socket and read JSON, or read what a sink wrote to S3-compatible storage, Azure Blob, an HTTP endpoint, a Zenoh data fabric or a file. A transform emits Cursor-on-Target.

Where it runs, and what it reads

One process, mind, from one archive per platform with nothing to install on the target. The standard Linux build (glibc 2.31 or later) and the fully static one are built and run on x86-64; the 64-bit Arm Linux, macOS and Windows archives are built in CI; not run locally. The same decoder reads CAN-style frames; a SocketCAN capture source is designed, not built.

Try it in five minutes

Needs a Rust toolchain, a C/C++ compiler, CMake and the libpcap headers.

git clone https://github.com/USAREUR-AF/first-bite && cd first-bite
make build

# Validate a dictionary and run its test vectors.
cargo run -p bite -- check dictionaries/weather-station

# Decode one payload by hand.
cargo run -p bite -- decode dictionaries/weather-station --port 40100 \
    0200174b583700fb2e18bcda9b4236000004030201beef

# Replay a capture file through the whole pipeline.
cargo run -p mind -- --pcap-file examples/weather-station.pcap \
    --dictionary dictionaries/weather-station --output

To decode traffic your own network already carries, capture the Network Time Protocol with the ntp dictionary: sudo ./target/debug/mind eth0 --dictionary dictionaries/ntp --filter "udp port 123".
